# 架构说明

这份文档讲**代码怎么组织、数据怎么流、状态存在哪**。用法看 `usage.md`，
为什么这么设计看 `design-notes.md`。

---

## 1. 一条主线

所有命令最终都落在同一句话上：

> **取到一份内容 → 解析成表 → （可选）提交进数据集 → 生成报告**

`flow.py` 是这条线唯一的实现。命令负责取参数、取内容、展示结果；
它不许自己写数据集。

```
                 ┌──────────────┐
   --url ───────▶│  ladder.py   │  A: http → B: browser → C: desktop
   --text-file ─▶│  (选通道)     │  每次失败都带具体理由，不猜
   剪贴板 ──────▶└──────┬───────┘
                        ▼
                 ┌──────────────┐
                 │  Captured    │  kind: text / html / json
                 │  models.py   │  + 来源、实际页面、通道、引擎
                 └──────┬───────┘
                        ▼
                 ┌──────────────┐
                 │  core.py     │  parse_capture(cap, card)
                 │              │  有卡 → 卡决定边界与字段
                 │              │  无卡 → infer 阶梯决定，并回吐卡草案
                 └──────┬───────┘
                        ▼
                 ┌──────────────┐
                 │  ParseResult │  rows / unparsed / notes / deviations
                 └──────┬───────┘
                        ▼
          ┌─────────────┴──────────────┐
          ▼                            ▼
   ┌──────────────┐            ┌──────────────┐
   │  report.py   │            │  flow.py     │
   │  人看的报告   │            │  Committer   │
   └──────────────┘            └──────┬───────┘
                                      ▼
                              ┌──────────────┐
                              │  dataset.py  │  pages/ + rows + 状态
                              └──────┬───────┘
                                     ▼
                              ┌──────────────┐
                              │ render/*     │  csv / md / jsonl / xlsx
                              └──────────────┘
```

## 2. 模块职责

### 入口层

| 文件 | 职责 | 不做什么 |
|---|---|---|
| `cli.py`（约 1100 行） | 参数定义、子命令分发、报告打印 | 不解析、不写数据集 |
| `__main__.py` | `python -m clip2table` | — |
| `capabilities.py` | 一张能力表，校验 / 分发 / 帮助文案共用 | 不做取数 |

`cli.py` 大是因为它要装下 9 个子命令的参数与展示，但每个子命令的实现都很薄：
取参数 → 调 `flow` 或 `core` → 打印。

### 取数层（通道）

| 文件 | 职责 |
|---|---|
| `ladder.py` | 三档降级：A 直连 → B 浏览器 → C 桌面。**判定依据必须可报告** |
| `channels/http.py` | 直连取页面 |
| `channels/cdp.py` | Chrome DevTools Protocol 客户端（手写 WebSocket 之上的最小封装） |
| `channels/ws.py` | WebSocket 帧编解码（RFC6455，仅文本帧，零依赖） |
| `channels/keyboard.py` | Win32 按键：`SetForegroundWindow`、`SendInput`、焦点记录与归还、窗口身份校验 |
| `channels/clipboard.py` | Win32 剪贴板读写（TEXT / CF_HTML / TSV），序列号变化检测 |
| `channels/cfhtml.py` | 把 CF_HTML 片段还原成 HTML |
| `harvest.py`（约 980 行） | 一轮采集的编排：聚焦 → 选全 → 复制 → 读剪贴板 → 解析 → 翻页 → 停 |

`harvest.py` 是唯一同时知道"怎么按"和"按完要等什么"的地方。它不决定数据怎么切。

### 解析层

严格按顺序，每一步只做一件事：

| 阶段 | 文件 | 输入 → 输出 |
|---|---|---|
| 1. 判形 | `pipeline/sniff.py` | `Captured` → 文本/HTML/JSON 的实际形态 |
| 2. 归一 | `pipeline/normalize.py` | 原始文本 → 去控制字符、统一空白与换行 |
| 3. 切分 | `pipeline/segment.py` | 行 → 记录边界（S0–S4 阶梯 + 区域周期） |
| 4. 抽值 | `pipeline/extract.py` | 记录 + 字段规则 → 每字段的值与来源行 |
| 5. 组装 | `pipeline/assemble.py` | 记录 → `Row`，同时算未识别与守恒 |
| 6. 推断 | `pipeline/infer.py` | 无卡时反推结构、报歧义、生成卡草案 |

`segment.py`（539 行）是全场最难的：**"记录从哪开始"只能靠启发式**。
它内部按证据强弱排成阶梯（S0 表格 → S1 周期 → S2 键值 → S3 编号 → S4 无结构），
并且要求周期检测必须**有对比**（不同偏移位置的形状类不能全一样），
否则一个平铺的页面会被编造成"每 2 行一条"。

### 数据层

| 文件 | 职责 |
|---|---|
| `models.py` | `Captured` / `Row` / `ParseResult` / `FieldTrace` / `Conflict` |
| `dataset.py`（约 1360 行） | 页提交、去重、冲突分类、状态、卡快照绑定 |
| `flow.py` | 提交边界的唯一入口（`Committer`） |
| `tasks.py` | 任务创建、样本确认、修正与运行记录；首次配置耗时和成功重跑次数 |
| `taskflow.py` | 任务向导与规则修正：生成卡文本、`Fix`、整批效果对比 |
| `preview.py` | 预览：表格 + 字段来源行 + 原文归属，全在终端里 |
| `report.py` | 报告文本 / JSON 的渲染 |

任务命令复用解析与采集入口。`taskflow.py` 收集配置，`marks.py` 将原文标记转换为规则，
`preview.py` 展示结果，`tasks.py` 将过程记录写入 `<任务名>.stats.json`。
候选分段以 `periodic` 保存到卡片，由 `core.parse_capture` 统一执行。

### 卡与渲染

| 文件 | 职责 |
|---|---|
| `cards/schema.py` | TOML → `Card`，全部校验在这里 |
| `cards/emit.py` | 字段与分段的 TOML 序列化，供任务创建和局部修正共用 |
| `cards/loader.py` | 内置卡与外部卡的定位 |
| `cards/regress.py` | `test` 子命令：样本 + 独立答案键比对 |
| `render/text.py` | CSV / Markdown / JSONL |
| `render/xlsx.py` | 自写 xlsx（`zipfile` + Sheet XML，零依赖） |

## 3. 数据流的关键约定

### 一个值没找到，就是 `None`

不补、不猜、不从邻行借。空缺率是信息，填平了就看不出来。

### 每行源文本必须有所属

`ParseResult` 里 `rows` 与 `unparsed` 是互补的：源行数 = 被记录认领的行 + 未识别行。
`assemble.py` 每次都会算这个账，报告里那行 `✓ 行数守恒` 就是它。

### 字段要能溯源

每个字段在 `FieldTrace` 里带三样东西：**类型**、**来源行号**、**为什么空**。
"空"是七种不同的事实，不是一种：

| status | 意思 |
|---|---|
| `ok` | 取到了 |
| `missing` | 规则跑完了，这条记录里没有这个东西 |
| `out-of-range` | 规则指到记录外面去了（要第 9 行，记录只有 3 行） |
| `no-match` | 有文本，正则没匹配上（含太短、命中排除词） |
| `coerce-failed` | 取到文本了，但不是声明的类型（`int` 字段拿到"面议"） |
| `unimplemented` | 这个版本没有该原语的生产者 |
| `rule-error` | 规则本身报错（运行时正则异常） |

前四种都会表现为一个空格，含义却完全不同：用户该改的是页面、是正则、还是类型，
取决于哪一种。

### 卡声明的东西必须能执行

`capabilities.py` 是一张表，`cards validate`、实际分发、`cards show` 三处共用它。
所以"卡里写了 `kind = "dom"` 但这个版本做不到"会在校验阶段就被拒绝，
而不是运行时静默返回空。

## 4. 持久化：dataset 长什么样

```
data/mysite/
├── pages/                  # 唯一真相
│   ├── .tmp-0007/          # 正在构建，没人读
│   └── 0007/               # 已发布，不可变，永不重写
│       ├── raw.txt         # 原始文本，一字不改
│       ├── meta.json       # 来源 / 实际页面 / 通道 / 引擎 / 行数 / 指纹 / 卡快照 / 续采位置 / 偏离
│       └── rows.json       # 带类型的值 + 每字段溯源
├── rows.csv                # 累计表（派生，可 rebuild）
├── state.json              # 已见主键、已提交页、卡快照（派生，可 rebuild）
├── manifest.json           # 每次采集运行一条
└── conflicts.json          # 冲突明细，不是只打印（有冲突时才写）
```

### 为什么以「页」为提交单位

早先的版本每页写四个文件（raw / rows.csv / state.json / manifest），每个写入都是原子的，
**组合起来不是**：在替换 `rows.csv` 和替换 `state.json` 之间被杀掉，目录会说"第 3 页完成"
而里面装的是第 2 页的行。这种状态**看起来不坏**，所以最危险。

现在一页是先建到 `.tmp-0007/`，整页成功才一次 `rename` 成 `0007/`。单文件系统上 rename 是原子的，
所以一页要么完整存在，要么不存在。`rows.csv` 与 `state.json` 由已提交的页**派生**出来，
随时 `rebuild()`；两者与 `pages/` 不一致时以 `pages/` 为准——它是证据，另外两个是视图。

`meta.json` 里同时记了 `requested_url` 和 `observed_url`。桌面通道读不到地址栏，
如果拿请求 URL 冒充来源，就会出现"解析整齐、守恒通过、来源是错的"。

### 冲突分两种

| 类型 | 判定依据 | 默认处置（`report_only` / `keep_first`） |
|---|---|---|
| 内容变更 | 卡声明的身份字段没变，变的只是其它字段 | 保留先到的那条，新值进 `conflicts.json` |
| 身份冲突 | 卡声明的身份字段变了 | 保留先到的那条，另一条进 `conflicts.json` |

"保留先到"而不是"保留最新"，是因为同一次采集里"更晚读到"不代表"更权威"：
两个页面先后给出同一订单的不同金额，工具没有依据判断哪个是真的，替用户选
就是把一次真实分歧变成一次静默覆盖。要两份都留在表里，用 `on_collision =
"keep_all"`（新版本标 `_dup_of`，同一版本不会重复追加）。

判定只能由卡给出。数据本身分不清"一条记录改了很多字段"和"两个不同记录撞了
一个键"，所以卡可以声明：

```toml
[dedupe]
key = ["订单号"]
identity = ["订单号", "下单人"]   # 这些变了 = 不是同一条记录
mutable  = ["状态", "金额"]       # 这些变了 = 正常更新
```

没有声明 `identity` 时，工具不会替用户下"身份冲突"的结论，只在冲突条目里给出
`hint`（例如"4/5 个字段不同，主键可能选错（仅提示）"）。

### 续采位置按通道分别定义

`state.json` 记的是**页级位置**，而且"第 4 页"对三条通道不是同一件事：

| 通道 | 页号含义 | 能否恢复 |
|---|---|---|
| `http` | 请求参数 | 记下就够 |
| `browser` | 地址可知（CDP 读 `location.href`），记下实际落到的 URL | 能 |
| `desktop` | **地址不可知，滚动位置没有任何 Win32 调用能还原** | 不能 |

所以桌面通道续采必须显式 `--append-from-here`，新的一段以单独段号接在后面，
并在 manifest 里写明"接着当前屏幕继续"，**不假装页号能还原界面**。
不这么做的后果是把第 1 页重新采一遍、却当成第 4 页写进磁盘。

## 5. 报告：先写怎么拿到的

报告第一行固定是通道、引擎、判定依据；第二行是来源——而且来源有三种形态：
读到的就是这个地址 / 落地地址与请求不同（会把请求地址也写出来）/ 桌面通道读不到地址栏
（写"未知地址 ｜ 实际驱动的是窗口 '标题'"）。
理由很实际：同一个 `ParseResult` 可能来自 API，也可能来自你正在打字的那个窗口。
不写清楚，用户会以为自己拿到的是 API 数据。

## 6. 测试

`tests/` 按模块切分，共 539 项（`python -m unittest discover -s tests -t .`）。
有三类测试值得单独说：

- **守恒类**：任意输入下 `rows + unparsed == 源行数`。
- **对抗类**：故意构造"看起来像结构、其实没有结构"的输入（全短行、散落日期、
  一张表的导航栏），验证工具不编造。
- **回归类**：`cards/regress.py` + 卡自带样本 + 独立答案键，验证规则没被改坏。

`selftest` 拿 `SKILL.md` 与 `docs/` 里出现的子命令（含 `cards list` 这类两段式）和真实
argparser 对账，写错了非 0 退出；一份文档都找不到也算失败——它只校验仓库里的文档，
装好的副本里没有文档，那种情况下「跳过」等于什么也没查。
